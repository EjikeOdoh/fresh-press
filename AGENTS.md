# AGENTS.md — FreshPress Dry Cleaners

This file is the operating manual for any engineer (human or AI agent) working on this
repository. It is the **persistent source of truth** for how work must be performed.

## Project

For any question about scope, data model, business rules or acceptance criteria, see
`docs/PROJECT_SPEC.md`. For the phase-by-phase roadmap, see
`docs/IMPLEMENTATION_PHASES.md`.

Before modifying the application, **read both documents**:

```text
docs/PROJECT_SPEC.md
docs/IMPLEMENTATION_PHASES.md
```

## General

* You are working on **FreshPress Dry Cleaners** — a dry-cleaning service booking and
  order management website. It is **not** a generic e-commerce store.
* Implement **one phase at a time**, in the order defined in
  `docs/IMPLEMENTATION_PHASES.md`.
* Inspect existing code before modifying it.
* Do not rewrite working functionality unnecessarily.
* Do not skip phases. Do not silently drop a requirement to make a build pass.
* Do not fabricate credentials or invent successful results. If a value/config is
  missing, implement what is safe and report exactly what is required.

## Development

* Use TypeScript everywhere. No `any` unless unavoidable and commented.
* Keep this a single Next.js App Router full-stack application. There is no separate
  backend service (no NestJS).
* Reuse components. Shared UI primitives live in `src/components/ui` (shadcn/ui style).
  Shared business logic lives in `src/lib`, `src/actions` and `src/db`.
* Keep server-only code server-only: never import `src/lib/auth.ts`, `src/db/*`,
  `src/lib/mailgun.ts` or anything reading secrets from a `"use client"` module.
* Prefer Server Components; add `"use client"` only where interactivity demands it.
* Avoid unnecessary dependencies. Prefer the platform (fetch, FormData, Intl).
* Follow the existing project conventions (naming, file layout, formatting).

## Database

* Use **Neon PostgreSQL** (serverless) with **Drizzle ORM**.
* Every schema change must be captured as a Drizzle migration in `drizzle/`.
  Never hand-edit an applied migration; generate a new one.
* **Never use floating-point values for money.** All money is stored as integer
  **naira** (`integer` columns). See `docs/PROJECT_SPEC.md#money-representation`.
* The database is the source of truth for prices. Prices must never be hard-coded in
  the UI; they are read from `services`.
* `order_items.service_name` and `order_items.unit_price` are **historical snapshots**.
  Never "fix up" historic orders when a service changes.
* Use parameters/ORM query builders. Never interpolate user input into SQL.

## Authentication

* Use **Better Auth** with **Google OAuth** (Google is the only provider; there is no
  email/password auth).
* Better Auth's tables (`user`, `session`, `account`, `verification`) are generated by
  the Better Auth CLI and must live in `src/db/schema/auth.ts`. Never hand-invent them.
* Keep all secrets server-side: `BETTER_AUTH_SECRET`, `GOOGLE_CLIENT_SECRET`,
  `MAILGUN_API_KEY`, `DATABASE_URL` must never reach the client bundle.
* Enforce authorization on the server (page/route/action level). Middleware is only an
  optimistic redirect, never the security boundary.

## Checkout

* **Never trust client-submitted prices or totals.** The server recalculates every line
  total, subtotal, delivery fee and total from the database.
* Order creation must run in a **single database transaction**: create order, create
  order items, clear the cart, commit.
* Order numbers are human readable (`FP-YYYYMMDD-NNN`) and must be unique at the
  database level.
* Duplicate submissions (double clicks, refreshes, retries) must not create duplicate
  orders.
* A customer may only ever see their own orders. Ownership is enforced in the SQL query,
  not only in the UI.

## Email

* Use **Mailgun** for the order confirmation email (HTML + plain-text fallback).
* An email failure must **never** destroy, roll back or delete a successfully committed
  order. Record `confirmationEmailSentAt` and log failures.

## Verification

After every phase:

* Run TypeScript checks: `npm run typecheck`
* Run ESLint: `npm run lint`
* Run relevant tests: `npm run test`
* Run the build when appropriate: `npm run build`
* Fix all errors before declaring the phase complete.

## Reporting

After every phase, report exactly these sections:

```text
Completed
Files Changed
Verification
Issues
Next Phase
```

Do not automatically start the next phase after reporting.
